Llama GUI — Architecture

A visual map of how Llama GUI is put together: a dependency-free Python control plane that installs and supervises llama.cpp binaries, and a bundler-free browser UI that drives it. This document is a guide for users who want to understand what the app does behind the buttons, and for developers who need to know where a change belongs before making it.

Overview

Llama GUI is a launcher and control panel, not an inference engine. It never loads a model itself. Everything that touches weights happens inside a llama.cpp binary that the app downloads, verifies, and runs as a child process. The Python layer exists to do the things a browser cannot: fetch GitHub releases, unpack archives, spawn processes, read stdout, open native file dialogs, and run git.

Three deliberate constraints shape the whole codebase:

No web framework

The backend is http.server.ThreadingHTTPServer plus a 75-line router. A user with Python and three pip packages can run the app — there is no Flask, no FastAPI, no ASGI server to install or configure.

No bundler

The frontend is 25 ordered <script> tags that each attach a namespace to window.LlamaGui. There is no build step: edit a file, reload the page. Node and Playwright are test-only dev dependencies.

One source of truth per concept

Every launch setting lives once, in flagCore. Every CLI flag is defined once, in FLAGS. Every color lives once, in tokens.css. Mirrored controls read and write the same object rather than keeping copies.

Service injection

BackendServices is a dataclass of callables that starts out filled with a _missing_service stub that raises. At import time configure_services(APP_CONTEXT) replaces each field with the real implementation. Routes never import services directly — they reach them through ctx.services, which is what lets the backend test suite swap in fakes for platform-specific behavior (binary suffixes, otool, ldd, tkinter) without touching the routes. 

# every route has the same shape
def get_status(request, response, ctx):
    snapshot = process_manager.get_process_status_snapshot(ctx)
    ...
    return response.json(payload)

# ctx carries everything a route may need
ctx.paths      # frozen AppPaths   — llama/, models/, presets/, config.json
ctx.config     # frozen ServerConfig — hosts, ports, GitHub API, release branch
ctx.state      # mutable ServerState — process, locks, buffers, generations
ctx.services   # injected BackendServices — platform + IO callables

6

7

Response — JSON, or an SseWriter for chat streamingOn failure the real exception goes to stderr; the client gets sanitize_error() output with no paths or internals.

Static requests take a shorter path: ui/ is served directly, with a manifest of known asset paths and a cache-busting query parameter applied after an app update so a stale app.js can never survive a version change.

State & concurrency

The backend is threaded — ThreadingHTTPServer gives every request its own thread, and installs, downloads, tunnels, and output readers add more. All mutable state is therefore centralized in ServerState and guarded.

Locks

  • process_lock — the single process slot
  • output_buffer_lock — stdout ring buffer
  • install_lock — one install at a time
  • model_download_lock — one HF download
  • remote_tunnel_lock — tunnel lifecycle
  • llama_api_target_lock, external_chat_target_lock
  • runtime_health_lock, config_lock

AtomicDict

A lock-protected dict used for every status payload the frontend polls. Mutating methods return a copied post-mutation snapshot, so a caller can act on the new state without holding the lock.

update() · replace() · snapshot()

Generation counters

Two monotonic counters make stale browser tabs safe. Every launch increments runtime_generation, and every process start increments output_generation.

  • Output cursor. /api/output is polled with a since cursor and returns the authoritative generation with each chunk. A tab holding output from a process that has since been replaced sees the generation change, discards its buffer, and re-syncs — instead of interleaving two runs' logs.
  • Readiness. Health checks are keyed to an expected generation. A readiness reply for a superseded launch is reported as superseded rather than being mistaken for the current server coming up.
Windows process stop. Sending CTRL_BREAK_EVENT requires CREATE_NEW_PROCESS_GROUP at creation time. Without it the signal can reach the parent process when the two share a console — which is why the creation flags and the stop path have to be read together.

Dependency injection, frontend-style

Feature modules do not reach for globals. app.js calls each module's configure() and hands it what it needs — fetchJson, flagCore, confirmation callbacks, status helpers. That is what makes the .cjs unit tests possible: they load a module's source inside a node:vm context with stub dependencies, no browser required.

Realm caveat. Because those tests run source in a vm context, instanceof is unreliable for values crossing the realm boundary. Duck-type instead — check for .has and .size rather than x instanceof Set, and use Array.isArray.

The rule has three corollaries the codebase enforces:

  • No per-tab copies of flag, template, or sampler state — and no second options list for a duplicated control.
  • The command preview is generated only from shared state. If the preview and the launch could ever disagree, the preview is worthless.
  • If a mirrored control cannot be kept reliable, delete the duplicate UI rather than maintain two sources of truth.

Flag system

ui/js/flags/definitions.js holds FLAGS, the single source of truth for every llama.cpp option the UI exposes — 1,816 lines of pure data with no rendering logic. Each entry carries an id, the CLI flag, a category, a type, label and description text, a tool scope, and a default.

Types

  • bool — checkbox; false_flag emits the negated form (--no-mmap)
  • int / float — numeric with min/max/step
  • text — free-form
  • text_list — one value per line, flag repeated per value
  • path — text plus a native Browse button
  • enum — dropdown from a shared options list
  • multi_enum — checkboxes, with risk: "high" badges

Categories

model · context · cpu · gpu · auto_fit · sampling · rope · conversation · lora · kv · speculative · server · mcp · grammar · logging · advanced

Any flag may declare submenu to render inside a collapsible sub-accordion; a category may declare submenuOrder to control the order those blocks appear in.

Display order and argument order are different things. submenuOrder is presentation-only. The FLAGS array order determines CLI argument order in the built command and must never be shuffled for layout reasons. tests/frontend/flag_definitions_unit.cjs fails the build if the two drift apart.

Presets: designed for scale

The reference case is 58 presets across 33 model groups, and several decisions only make sense at that size. Groups are collapsed by default. Search text is precomputed onto each entry rather than rebuilt per keystroke, and flag labels are cached in a Map keyed on the FLAGS array identity. The list is a single composite widget with roving focus: at the reference size the naive markup would have been 265 tab stops, and it is now one.

Missing-model detection is deliberately conservative. A bare filename held by two subfolders reports as ambiguous rather than resolving — guessing a folder would launch the wrong weights. An unknown model list, an empty models folder, and a preset with no model all stay silent, because a preset for a model kept on another machine is legitimate.

Updating the app itself

GET /api/app-update-status runs git fetch origin --prune --prune-tags --tags. The Stable channel finds the newest release tag reachable from origin/main; the Nightly channel targets the latest origin/main commit directly — always the release branch, never the checked-out branch, so a user on a development branch is still compared with the selected Stable or Nightly target. Tags are selected by version sort, not date, because they are lightweight and a hotfix tagged onto an older commit would otherwise sort wrong.

Dirty working-tree paths are classified: data and cache locations (models/, presets/, llama/, config.json, __pycache__/, log and backup suffixes) are safe; source changes are blocking. If the branch is behind and nothing blocks, POST /api/app-update fast-forwards to the selected tag or branch head, reinstalls requirements.txt, restarts the server, and the page reloads with a cache-busting timestamp.

stateMeaningAuto-update
up_to_dateHEAD already contains the selected tag or branch head, including local commits made after itNo
behindThe selected target is a strict descendant of HEAD, so merge --ff-only can succeedYes, unless blocking changes exist
divergedHEAD and the selected target have both moved; manual merge or rebase requiredNo
no_releaseNo tag on the release branch matched the release patternNo
errorA git command failed or the upstream branch is missing; reason holds the detailNo

Security boundaries

Llama GUI binds to loopback by default and is designed for a single trusted user on their own machine. The boundaries it does enforce are worth understanding before exposing it further.

CORS & origins

API access is restricted to loopback origins for the configured GUI port, trusted LLAMA_GUI_ALLOWED_HOSTS entries when wildcard-bound, and the active tunnel URL. The check runs before routing.

Proxy target policy

The chat and metrics destination is resolved from backend state, never from the request body. Registration goes through the same local-address check as the metrics proxy — only loopback and this machine's own interfaces — and is probed with GET /health before acceptance. The enforced boundary is the address policy, not the caller.

Unattended restore

Re-adopting a remembered target requires the /health response to actually look like llama.cpp's. If another local service has taken the port since the last session, the restore is refused instead of silently proxying chat to it. A hand-driven connect stays permissive.

Input validation

HF repo IDs, revisions, and filenames pass strict regex and traversal checks; only .gguf can be downloaded. Archive members are path-checked before extraction. Model paths reject absolute paths and .. segments. Errors reaching the client go through sanitize_error(); the real exception goes to stderr.

What --api-key protects. It secures llama-server, not the Python management UI. And because the key is passed as a process argument, same-user OS process inspection can still reveal it.

Theming

A theme is exactly two things: one palette block in ui/css/tokens.css and one entry in the THEMES registry in ui/js/theme-ui.js. Nothing else. style.css contains no color literals and no [data-theme=…] selectors — both are absent by design, and theme_ui_unit.cjs will not let a new theme quietly render as the fallback.

Contrast floors are enforced per theme — WCAG AA for text, 3:1 for --fg-faint and the fill-only -solid tokens — measured against --bg-surface, --bg-raised, --bg-elevated, each semantic color's own -subtle chip, and composited interaction-state washes. On a mid-tone theme like Graphite the subtle chip sits lighter than the surface, so its colors need brightening exactly where a light theme needs darkening.

Adding a llama.cpp flag

  1. Confirm the flag upstream in common/arg.cpp or server.cpp — name, shorthand, value type, valid enum values, and whether it has been renamed or removed.
  2. Add an entry to FLAGS in ui/js/flags/definitions.js, matching enum values exactly and setting false_flag for negated booleans.
  3. Run npm run test:flag-definitions.
  4. Check the generated command preview produces arguments llama-server actually accepts.

Adding a backend endpoint

  1. Put the logic in a service under backend/services/, taking ctx and mutating state only under its lock.
  2. Add a thin route function (request, response, ctx) in the matching backend/routes/ module.
  3. Register it in the Router chain at the bottom of backend/app.py.
  4. Validate all external input before it reaches the filesystem or a subprocess; sanitize errors to the client and print the real one to stderr.
  5. Add coverage in tests/backend/ and run python -m unittest discover tests -v.

Adding a frontend module

  1. Create the file under ui/js/ and attach it to window.LlamaGui.<name> — no new globals on app.js.
  2. Add the <script> tag in ui/index.html after its dependencies and before its consumers, and mirror the order in docs/directory.md.
  3. Take dependencies through a configure() call from app.js rather than reaching for globals.
  4. Write launch-relevant values through flagCore setters. Never mutate flagValues directly.
  5. Use textContent for anything user- or model-supplied. Add a .cjs unit test and run npm test.
